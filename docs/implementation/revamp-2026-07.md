# July 2026 Revamp

This document describes the architecture and product decisions from the July 2026 revamp.
Where older documents (PRD sections on sync, the external-sync safety guidelines, the
implementation plan) disagree with this document, **this document wins**.

## What changed and why

The v1 implementation had three structural problems:

1. **A god-object store.** `store.ts` (~1,200 lines) mixed UI state, Dexie queries, business
   logic, Google Sheets orchestration, and `alert()`/`confirm()` calls.
2. **Spreadsheet-as-database sync.** Bidirectional Google Sheets sync with identity probing,
   legacy adoption, repair operations, and conflict detection was ~40% of the app's complexity
   and the main source of breakage.
3. **Prototype-grade UI.** Inline styles, browser popups for all dialogs, unfinished
   placeholders, no component layer.

## New sync model: the app is the source of truth

Google Sheets is a **dumb export/import target**, not a peer.

- **Export** overwrites the linked sheet with the class's local data in one batch write
  (`values:batchUpdate`). If no sheet is linked or it was deleted, a new one is created.
- **Import** reads all tabs in one batch, validates them (structure, duplicates, referential
  integrity, single-class consistency), shows the user a summary, and — only after explicit
  confirmation — overwrites the class's local data. Rows are always re-homed to the current
  class; the only class-level rule is that a sheet must not mix rows from multiple classes.
- Nothing is merged, reconciled, or repaired. `lastExportedAt` is informational only.

Removed entirely: identity probe, adopt mode, "repair sheet metadata", legacy-format handling,
export conflict warnings, the File System Access CSV output (History's CSV export covers that
need), and per-row `appendRows` loops.

## Layered architecture

```
domain/    Pure functions, no I/O. sampling.ts, attendance.ts, sessionDraft.ts,
           validation.ts, sheetImport.ts. Fully unit-tested.
data/      db.ts (Dexie schema) + repository.ts. The ONLY module that touches IndexedDB.
services/  sheetsClient.ts (OAuth + generic Sheets ops) and sheetsSync.ts
           (CheckPoint export/import). No DB access, no UI.
store.ts   Thin Zustand store: class selection, session lifecycle, settings, and sync
           orchestration. Actions return typed results ({ ok } | { ok:false, error }).
pages/     Presentation. May read via the repository; all mutations go through the store
           or repository. All dialogs/toasts live here (useConfirm / useToast).
```

Invariants:

- No `alert()` / `confirm()` anywhere — `components/Dialog.tsx` and `components/Toast.tsx`
  provide `useConfirm()` and `useToast()`.
- No `await import(...)` inside Dexie transactions (the old `correctMark` bug).
- The selected class persists across reloads (`checkpoint_selected_class`), and draft
  sessions still autosave per class (`checkpoint_draft_session_<classId>`).
- The store exposes a `ready` flag; class-scoped pages wait for it before redirecting,
  so hard reloads on `/session` etc. work.

## Testing

- **Unit (vitest):** `npm run test:run` — domain layer (sampling, carryovers, draft
  building, sheet import parsing, row validation).
- **E2E (Playwright):** `npm run e2e` — the golden path: create class → import roster CSV →
  run a check with one absence → draft survives a reload → absent student carries over with
  a recheck badge → marking present clears the carryover → history shows both sessions.

## Known non-goals / leftovers

- The Sheets tab schema is unchanged from v1 (minus the `schemaVersion` column in Settings),
  so previously exported sheets still import.
- No backend; cross-device use = export on machine A, import on machine B, both explicit.
